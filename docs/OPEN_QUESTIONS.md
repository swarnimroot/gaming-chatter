## Open from 2026-05-15 (Phase 3c.14)

- **No length cap on YouTube audio-fallback transcription.** When captions fail, the upstream `fetch_youtube_transcript(url, audio_fallback=True)` downloads + transcribes the full audio regardless of duration. CPU cost scales linearly: `~30–50 s of small.en CPU per audio-minute`. A 90-min livestream would burn ~45–75 min of CPU on a single item — invisible during an overnight APScheduler run, blocking on the interactive Run-pipeline button. Not a problem in our current channel mix (all short-form: trailers + 5–15 min guides), but the moment a podcast/interview/livestream source is added, this becomes a real blocker. Fix options when it bites: (a) pre-fetch video metadata via yt-dlp `--dump-json` and skip-or-flag items > N minutes; (b) ask scrapers-lib to expose a `max_duration_seconds` kwarg; (c) feature-flag audio fallback off for sources flagged as long-form. Defer until a long-form source is actually proposed.

- **No quality floor on returned transcripts before sending to Haiku.** `app/services/enrich.py:_body_for_enrichment` only checks `if transcript:` (truthy = non-empty). A 50-char gibberish transcript from a silent/music-heavy trailer would pass and feed Haiku noise instead of the more-informative video title. Not observed as a real failure mode in the 2026-05-15 backfill (the noisy horror-trailer transcript was 115 chars and Haiku tagged it correctly using title context), but the risk is real. Fix options: (a) tighten the truthiness check to `len(transcript.strip()) > N` (cheap, blunt); (b) compute a simple readability/diversity heuristic (token entropy, repeated-token ratio) and fall back to title/body below a threshold; (c) prepend the title to the transcript so Haiku has both signals (best of both worlds — costs ~50 prompt tokens per YT item). Defer until a real bad-transcript-induced mistag is observed in the wild.

- ~~**`scripts/rerun_enrichment.py` post-run diff print crashes on emoji titles under Windows cp1252.**~~ **Resolved 2026-05-15 (Phase 3c.14 close-out).** Added `if hasattr(sys.stdout, "reconfigure"): sys.stdout.reconfigure(encoding="utf-8", errors="replace")` at the script's entry block (after the `sys.path` bootstrap, before `logging.basicConfig`). Defensive `hasattr` guard for the rare case where stdout has been swapped to a non-TextIOWrapper (won't matter for the CLI script's normal usage but keeps the fix free of edge-case crashes). Fix is in-place at `scripts/rerun_enrichment.py:21-22`.

## Open from 2026-05-19 (Phase 3c.18)

- **Annual URL update for `refresh_pcgamer_releases.py`.** Default URL `https://www.pcgamer.com/games/new-pc-games-2026/` is year-stamped; the 2027 page will have a different slug (likely `new-pc-games-2027`, but pcgamer's URL conventions aren't formally documented). The `--url` arg lets us override per-run today, so this is a low-urgency calendar item rather than a code bug. Could be automated as a Phase 4 nicety (probe both `-N` and `-N+1` slugs, pick whichever 200s).

- **Haiku run-to-run drift on the pcgamer ingest.** Run #2 immediately after run #1 on the same article body showed 0 new / 1 updated / 285 unchanged — i.e., one entry's `release_date` flipped between identical runs. LLM non-determinism, not a bug. Tolerable at 1/286 = ~0.3% drift per refresh; watch over time. If drift starts compounding (e.g., 5–10 entries jittering on each refresh), tighten the prompt or add a 2-of-3-runs majority pass. The cost of majority would be 3× per refresh (~$0.12/run instead of ~$0.04), still affordable at weekly cadence.

- **IGN release-date ingestion not yet built.** The `game_releases.source` column was designed multi-source from day one (`'pcgamer' | 'ign'`) and `SOURCE_PRIORITY = ['pcgamer', 'ign']` is already coded in `app/services/release_dates.py`. A parallel `scripts/refresh_ign_releases.py` (~50 LOC, same shape) is stub-ready. Defer until: (a) pcgamer drift becomes noisy enough to want a second source for cross-check, OR (b) a specific game is missing from pcgamer and we want IGN as fallback. Phase 3c.1's earlier IGN scrape dead-end (React/Next.js rendered, 1/5 sample games in static HTML) is the open risk here — the trafilatura + Chrome impersonation path used for pcgamer may or may not work against IGN's release-date pages; a quick probe should precede script work.

- **No ETag/Last-Modified short-circuit on pcgamer refresh.** Haiku is called on every invocation regardless of whether pcgamer changed. At ~$0.04/run and roughly weekly cadence, the headroom is ~$2/yr — not worth the complexity in v1. Deferred to Phase 4. Implementation when it lands: store `pcgamer.etag` + `pcgamer.last_modified` after each successful fetch; on next run, send conditional `If-None-Match` / `If-Modified-Since` headers; 304 → skip Haiku entirely, just bump `game_releases.updated_at` on existing rows. ~20 LOC + a small `external_sources` table.

- **Drop `games.release_date` + `games.lifecycle` columns + refactor consumers.** Currently kept as a synced cache (overwritten by `sync_games_dim(...)` after each `game_releases` refresh). Consumers — Release Radar card, `top_games_for_week`, lifecycle chips on Hottest games — read these columns directly. A cleaner architecture would have consumers JOIN through `release_date_for(session, name)` + `derive_lifecycle(...)` on the fly. Defer until: (a) the synced-cache drift becomes a visible bug (e.g., a game that ships on a day the script didn't run shows stale 'upcoming' until the next refresh), OR (b) we add a second authoritative source (IGN) and the cache-priority logic gets messy. v1 cache approach was the right call for blast-radius minimization; the refactor is a known-future cleanup pass.
